# 饮食运动打卡 App：产品方案与路线图

> 本文是**产品定义文档**，不是代码改动计划（设计/开发尚未开始，你说过设计"暂时不急"）。先锁定范围与取舍，后续再进入设计与实现。

## 默认战略【已锁定 2026-06-05】
- 主打人群：**减肥/体重管理**；健康指标关注作为差异化次要层；慢病做成**非医疗轻量提醒 + 免责声明**。
- 平台：**iOS 优先**（HealthKit + Apple Watch + Widget），Android 后置。
- 市场：**只做海外区，当前不计划上中国区**（可重新评估），但**产品支持中文用户**（双语 i18n + 中式食物数据）。这样省掉 ICP 备案/国内主体/国内云/国内支付/推送/医疗资质一整摊重活，同时不放弃中文用户。务必区分"**服务中文用户**（做）"与"**中国区上架/合规**（不做）"。
- 商业模式：**Freemium + 订阅**（RevenueCat）。

## 核心设计原则
- 记录要**快**（记录摩擦是这类 App 头号死因）：拍照 / 常吃模板 / 条形码 优先于语音。
- 数据要**诚实**：AI 只做"识别食物 + 估份量"，营养数值**查食物数据库**；结果一律**可编辑**，展示估算/区间而非假精确。
- 文案要**温和**：避免惩罚式红色、紧迫式施压（减肥人群对负反馈敏感，存在饮食失调风险）。
- 指标**随人群自适应**：减肥看热量+三大营养素；健康关注层看糖/钠/纤维。

## 食物视觉方案（替代 AI 实时生成）
- 不做"一食物一图"，不需自行绘制大量食物图。
- v1 方案：**品类图标集（30–50 个，按品类映射，取自 SF Symbols / Twemoji / Icons8 等）+ 用户真实照片**（拍照即用真图，无图则用品类图标）。
- 包装食品走条形码时可用 **Open Food Facts 自带商品图**。
- 想要统一插画风时，后期**一次性生成 30–50 个品类插画固定复用**（与"运行时实时生成假图"区别开，前者可控、不持续烧钱）。

### 图标匹配机制：品类兜底 + 三层 fallback
- 不按"食物名查 emoji"（emoji 非为食物分类设计，可乐/奶茶/螺蛳粉等大量食物无对应 emoji）。
- 走 **食物 → 品类 → 品类图标**：品类是自己掌控的固定集合（30–50 个），每个品类预先绑定一个一定存在的图标，永不"找不到"。
- 三层 fallback：
  1. **常见食物关键词表**（可选，几百条，命中用更贴切图标，如 可乐→🥤、咖啡→☕、奶茶→🧋）。
  2. **品类图标表**（核心，必有）：未命中关键词则用数据库给出的品类对应固定图标。
  3. **终极默认**：连品类都识别不出，用中性占位图（如 🍽️ / 灰色餐盘图标）。
- 因最终都收敛到固定品类图标，**风格天然统一**（顺带解决早期担心的"图片风格乱"问题）。
- 注意 emoji 跨系统渲染样式不一致；若要视觉统一，用 **Twemoji 或自有品类图标资源**替代系统 emoji，机制相同。

## 明确砍掉 / 后置的点（守住"不四不像"）
- 永久砍：**运行时按每条记录实时 AI 生成食物图片**（无信息价值、烧钱、风格不一致问题的根源；改用上方品类图标 + 真实照片方案）。
- 砍：**月度热量上限进度条**（改用本周平均 / 7 天滚动趋势）。
- 砍：**精确减重预测、从照片预测血糖/升糖**（不准 + 打脸 + 合规风险；改为展示"能量缺口"和"平滑体重趋势"）。
- 后置：**社交/排名/点赞点粑粑**（对减肥人群有害、对慢病涉隐私；真做也只做好友私密圈 + opt-in，不做公开榜）。
- 后置：**日历双指缩放切换简洁/堆叠/详细**（炫技、成本高；先用 周/月/年 + 热力图）。
- 后置：图表自选样式、语音输入、多市场差异化。
- **砍：食谱 / Recipes（及餐单规划）**——内容产品、需持续运营、范围陷阱、不服务核心闭环；维持"不做食谱/餐单"既定取舍，v1 不做、不做 tab（远期可考虑精选/合作内容）。

## 关键技术选型
- 数据获取：**HealthKit**（主动消耗能量、步数、训练、心率、体重、睡眠）。
- 食物识别：视觉/多模态大模型识别食物与份量 → 映射到**食物数据库**取营养值。
- **食物搜索：分层合并搜**（按相关性优先级）：① 用户个人库/常吃/最近（本地优先，即时）→ ② 营养数据库（西式/品牌用商业 API 如 Nutritionix/Edamam/FatSecret）+ **中式食物成分数据集** → ③ 条码库（Open Food Facts，带商品图）→ ④ **AI 自由文本解析**（把整句拆成"食物+份量"再匹配，**跨语言兜底、中文用户尤其依赖此层**）→ ⑤ 手动添加自定义食物（存进个人库）。
- **双语 i18n（中英）从第一天就做**：UI + 搜索均支持中文（事后回改成本高）。中式混合菜估算更难，靠"结果可编辑 + 常吃模板"兜底，不承诺精确。
- 食物数据架构：不每次按键直打原始库；用**商业 API** 或把开源数据（USDA + Open Food Facts + 中式数据集）**预灌自建搜索索引**。v1 先用商业 API + 中式数据集快速上线，量大再自建索引控成本。
- 热量目标：**Mifflin-St Jeor 算 BMR → ×活动系数得 TDEE → 减肥制造 300–500 kcal/日缺口**。
- 体重趋势：**加权移动平均平滑**（参考 Happy Scale / Libra），用趋势代替预测。
- 订阅：**RevenueCat + Apple IAP**。
- 设计→代码：**Figma（含 Figma-Cursor MCP）出设计 → Cursor 生成 SwiftUI**；早期可用 v0 / Galileo 快速原型。
- **快速记录架构**：呈现无关的内容组件 + `QuickAddPresenter` 协议（`SystemSheet` / `CustomMorph` 两实现）+ feature flag；契约取两者公共集，系统版作可靠基线、自定义 Container Transform 藏 flag 后，可双向切换；自定义为签名级、早期出动画原型 de-risk。详见「添加 / 快速记录（"+" 完整逻辑）」。
- **食物数据源**：详见下方「食物数据源选型（v1）」一节。

## 食物数据源选型（v1）

核心结论：**v1 海外数据授权成本 ≈ 0**（FatSecret Premier Free + USDA + Open Food Facts 全免费/仅署名），真正花钱的是 **AI 推理** 和**自建索引的基础设施**。

### 分层数据栈（对齐「分层合并搜」）
| 层 | 来源 | 角色 | 成本/授权 |
|---|---|---|---|
| ① 个人库 | 本地（常吃/最近/自定义） | 即时、最高优先 | 自有 |
| ② 自建索引 | **USDA FoodData Central**（公有领域）+ **Open Food Facts**（ODbL）预灌进 Meilisearch/Typesense | 通用食物 + 控延迟控成本 | 免费（署名 + share-alike） |
| ③ 商用层 | **FatSecret Premier Free** | 美区全量 + 条码 + autocomplete + 食物图 | 免费（<$1M 营收/融资，需署名） |
| ④ 条码 | **Open Food Facts** | 包装食品 + 商品图（CC BY-SA） | 免费（署名） |
| ⑤ AI 文本/图像解析 | 多模态 LLM | 拆"食物+份量" → 映射回 ②③ 取营养值；跨菜系/中文长尾兜底 | 按量（LLM 调用） |
| ⑥ 手动自定义 | 用户输入 | 回流个人库/共享库 | 自有 |

### 拍照识别（已定 = 方案 A）
- **LLM 当识别器 + 自建库当真值**：视觉模型识别"食物名 + 份量估计" → 映射 ②③ 数据库取营养值。**与 ⑤ 文本解析共用一套管线**，跨菜系灵活、不锁厂商。
- 不用 FatSecret/Edamam 的 Vision add-on（按调用收费 + 锁厂商 + 中餐覆盖弱）。
- 结果一律可编辑、显示置信度与来源（沿用既定"来源标签 + 置信度"）。

### 中文食物数据（已定 = 方案 A）
- **人工精选 ~500–1000 条最常见中餐/饮品种子集**灌进自建库（参考公开成分资料整理，注意《中国食物成分表》有版权、不直接拷贝其库）。
- **长尾靠 ⑤ AI 拆解**（菜 → 食材 → USDA 值）+ **用户自定义回流**。
- **不承诺混合菜精确**，靠"结果可编辑 + 常吃模板"兜底。
- 不付费授权中式成分库（v1 太贵太慢，可 v2 重估）。

### 合规要点（锁进方案）
- **署名**：设置/关于页放"数据来源"页，列 FatSecret / Open Food Facts / USDA；每条记录沿用"来源标签"。
- **Open Food Facts**：衍生库 share-alike、商品图 CC BY-SA 均需署名。
- **缓存权**：FatSecret Premier Free 允许建自有日记/缓存；Edamam 低价层缓存受限——若仅作备用需先确认条款。
- **迁移预案**：营收/融资超 $1M 或需**非美区数据**时，迁移到付费 FatSecret Premier（初创 5 折）或自建索引扩容；接口层抽象好，换源不动上层。

### 备用/可选
- **Edamam Food Database**（$14–$69/月，90 万食物 + 68 万条码）作 FatSecret 的备用或补充；低价层注意缓存限制。
- **Nutritionix** 当前 $499+/月、无免费层，**v1 不用**。

## 关键技术 Spike（可行性验证）

三个高风险点，**写代码前先各做一个 time-box 的最小验证**，定"能不能做 + 怎么验 + 不过关的兜底"。优先级：① HealthKit（最确定）→ ② 拍照识别（最不确定、决定卖点）→ ③ 体重趋势（中等）。

### Spike 1 — HealthKit 读取边界
- **能不能做**：能。读取用 `HKHealthStore` 申请只读权限，按类型查询。
- **读哪些**：`stepCount`（步数）、`activeEnergyBurned`（主动消耗，**燃烧的真值来源**）、`HKWorkout`（训练类型/时长/能量）、`bodyMass`（体重）。可选：`basalEnergyBurned`（BMR，**只读不加进预算**）、`heartRate`、`sleepAnalysis`（v2）。可选回写 `dietaryEnergyConsumed`（把记录的食物写回健康 App）。
- **边界与坑**：
  - **隐私不可知**：Apple 不告知"读权限是否被拒"，被拒时查询**静默返回空**——无法区分"没授权"和"今天没数据"，**UI 必须对'无数据'优雅降级**，不能弹"请授权"误导。
  - **双重计算**：Apple Watch 的步数已计入 `activeEnergy`；若再用步数自己估热量并和 `activeEnergy` 相加会**重复计数**。规则：**有 `activeEnergy` 用它当真值，无表/无能量数据才退化到步数估算**。
  - **不灌水预算**：沿用既定原则，不把 BMR/运动消耗自动加进可吃额度（"吃回运动量"默认关）。
  - **后台更新**：`HKObserverQuery` + `enableBackgroundDelivery` 才能及时刷新。
  - **单位/多源**：用 `HKUnit` 处理 kcal/kJ、kg/lb；`bodyMass` 可能多来源（秤/手输），需去重 + 取最新 + 来源优先级。
  - **模拟器无健康数据**，必须真机（带/不带 Watch 各测）。
- **怎么验**：最小 app 申请上述 4–5 类权限 → 查"今日 activeEnergy + 步数 + 最近一次 bodyMass + 最近训练" → 打印；真机带 Watch / 不带 Watch / 拒权限 三种场景各跑一遍；验证后台投递能触发。
- **通过标准**：真机能读到今日主动消耗/步数/最新体重；拒权限/无数据时不崩不误导；燃烧总额无双重计数。
- **兜底**：拿不到 HealthKit → 步数手动/估算 + 体重手输，功能不阻断。

### Spike 2 — 拍照识别 + 查库精度（最关键，决定 AI 卖点）
- **管线**：照片 → 多模态 LLM 输出 `{食物名[], 份量估计, 置信度}` → 食物名映射营养库（USDA/FatSecret/自建）取营养值 → 可编辑确认页。
- **最弱环节 = 份量估计**：单张照片无深度参照，估"克数/份量"误差天然大。**产品对策：份量默认按'用户确认'，AI 份量只作建议**（给常见份量选项 + 可选参照物），**不自动信任份量**——这一条直接把精度风险降级（也和既定"可编辑 + 置信度"一致）。
- **怎么验（建基准集）**：收 ~50–100 张带标注食物照（西式 + 中式 + 包装混合），标注真值食物名 + 大致热量。指标：
  - **食物识别 Top-1 / Top-3 命中率**（名字对不对）。
  - **名字→库匹配命中率**（解析名能否落到正确库条目）。
  - **份量估计误差**（估计克数 vs 实际，MAE / ±X% 占比）——单独看，预期差。
  - **端到端热量误差**（最终 kcal vs 真值，落在 ±30% 内的占比）。
  - **延迟 P50/P95、单次成本**。
  - 同基准集横评 2–3 个模型（GPT-4o / Gemini / Claude）。
- **通过标准（建议）**：食物识别 Top-3 ≥ 80%；端到端热量在份量由用户确认的前提下 ±30% 内占比达标；延迟/成本可接受。
- **决策门 / 兜底**：若识别尚可但份量太差 → **走"AI 识别名字 + 用户选份量 + 查库取值"**（已是默认）；若整体识别也差 → 拍照降级为"打开确认页让用户搜/选"，照片仅作记录留存。**无论如何 AI 结果全可编辑、标置信度与来源。**

### Spike 3 — 体重趋势平滑算法选型
- **目标**：显示**诚实趋势**，不被每日水分噪声（±1–2 kg）带偏，也不做"必达 X 日"的硬预测。
- **选型**：**指数加权移动平均 EWMA**（Happy Scale / Libra 同款），半衰期约 ~10 天；**淡画原始点 + 粗画趋势线**；速率（kg/周）由趋势线在尾窗的斜率得出，配不确定区间。备选 SMA（有滞后）、线性回归斜率（算速率）、Kalman（过重，不做）。
- **怎么验**：用真实/合成体重序列（注入每日噪声 + 缺测 + 离群秤读数）跑 EWMA，对比 SMA / 回归斜率：① 趋势线在噪声下是否稳定不误导；② 速率估计是否接近注入的真实斜率（容差内）；③ 缺测/单点/离群的鲁棒性（离群剔除）。
- **通过标准**：趋势线在 ±1–2 kg 噪声下视觉平稳；速率估计匹配真实斜率；缺测/离群不崩不跳。
- **展示与合规**：呈现为"近 2 周 -0.4 kg/周"这类**描述性趋势**，避免硬 ETA 预测或给"必达日期"；如给预计达成，用**区间 + 免责**（呼应健康合规边界）。

## 首次引导（借鉴 MyFitnessPal，去其冗余，压到 4 步）
核心原则：**目标先行 → 先给价值（引导末尾立刻展示每日预算）→ 功能渐进式引出 → 注册/付费/社交后置**。

引导流程（每步分屏、不堆叠）：
1. **经验分层**（借鉴 Lose It）：先问"以前算过卡路里吗"→ 决定后续科普深度。铁律：**问了必须跟进**——选"没算过"的给新手解释 + 更低门槛首次记录；选"算过"的跳过科普直接进阶。（Lose It 的错就是问了却不跟进，把"怎么算"丢给用户，导致新手困惑。）
2. **目标多选**（减重 / 维持 / 增重 / 增肌 / 改善膳食 / 规划餐饮…，可组合）→ 决定首页主指标预置。
3. **基础信息**：年龄、性别、身高、体重、活动水平（分屏采集）。
4. **推荐目标确认**：用**命名档位**呈现（如 放松 / 稳重 / 加速 / 高强度，借鉴 Lose It），每档明确写"每天 X kcal + 每周减 X kg"，权衡一目了然；BMR/TDEE 计算，附保守/积极/手动选项。过激档位（每周 >0.7–1kg 或热量过低）给**安全护栏警示**，不让无脑选最猛。→ **立刻展示"我的每日预算"**（MFP 最关键的转化设计，先给价值）。
5. **记录习惯**：用餐提醒时间 + HealthKit 授权（带场景说明后再弹系统授权）。

引导结尾（修掉 Lose It "算完没人教"的坑，并立住差异化）：
- **一句安心话术**：核心卖点是"你不用自己数卡路里"——拍照/输入/选模板，App 帮你估算，随时可改。文案示例："不用自己算卡路里——拍张照或输入吃了什么，我们帮你估算，你随时能改。"
- **引导式首次记录**（借鉴 MFP guided first entry）：引导一结束立刻带用户记第一条，既教会用法又完成激活，新手不会卡在"那现在干嘛"。

目标 → 主指标的"轻分支"映射（共用同一引擎，仅换主指标/文案/卡片预置，**不衍生独立重功能**）：
- 减重 → 热量缺口、净摄入、体重趋势。
- 增重/增肌 → 总热量盈余、蛋白质、训练日。
- 改善膳食 → 三大营养素均衡、纤维/糖/钠提醒，弱化热量数字。
- 规划餐饮 → 侧重常吃模板/提前安排（v1 不做真正的餐单规划/食谱功能）。

明确不抄 MFP 的点：过长引导漏斗、采集 location、管理压力/冥想类目标、引导中强推付费/注册墙、"如何得知本 App"归因问题。注册/付费墙后置到**首次记录完成之后**，降低首跳流失。

教育/价值主张插页（借鉴 Yazio，**总量 2–3 屏封顶**，避免 Noom 式超长说服漏斗）：
- ✅ **溜溜球科普屏**：讲"过度节食→反弹+伤健康"，为我们的"温和缺口/安全护栏"背书。**红线：引用研究必须真实可核对，不摆假权威 logo。**
- ✅ **不忌口/定制价值主张屏**：传达"无需忌口、不用复杂规则、按你的生活方式定制"，契合低摩擦 + 不焦虑（视觉自有，不照搬 Yazio 配色）。
- ⚠️ **健康改善屏须去疗效化**：**禁止承诺具体疾病风险下降**（如"糖尿病/高血压/胆固醇降低"——违反健康关注层合规红线，海外 FTC/SaMD 高风险）。改为非疗效弱关联措辞，如"坚持均衡饮食与稳定体重，通常让你状态更好"；不点名疾病数值。此屏改造后**可选**，否则砍。
- 插页放在采集基础信息之后，让其显得"为你定制"；纯展示点"继续"即可，不增加输入负担。

## UI / 视觉设计原则（借鉴 Lifesum 的信息层级，坚持自有克制风格）
最高准则（用户原话）：**简约易用、布局清晰、美观大气**。

- **一屏一焦点**：首页中央就是热量预算环（Consumed / Remaining / Burned，**Remaining 最大**、行动导向），并**随预算状态变色**（安全绿 / 接近橙 / 超出红）。环下紧跟三大营养素条。
- **每餐给"推荐 kcal 区间"**（借鉴 Lifesum，如早餐 437–612），用区间不用死数字，顺带回答"该吃多少"。
- **卡片化 + 充足留白 + 大字号**，弱化营养术语，强调"还差多少 / 下一步"。
- **克制配色**：单一主强调色 + 中性灰底、轻渐变（不照搬 Lifesum 浓绿渐变顶栏）；**深色模式一等公民**。
- **人群预置 + 可编辑卡片**：喝水 / 蔬果 / 健康指标等做成**可开关卡片**，按人群默认、用户可增删排序，不默认全堆上。
- **【硬性原则】全 App 共用一套卡片化 Dashboard 骨架**（热量环 → 营养素条 → 餐次 → 活动 → Tab）。人群/健康关注**只改卡片的显隐、排序与主指标，绝不新建独立页面布局**。食物确认页的健康提示也是同页条件元素，非独立页面。避免"每类人一套页面"导致的设计/工作量膨胀。
- **正向微文案**：借鉴 Lifesum "Daily Wins" 式鼓励，而非超标惩罚式红字。
- **无障碍**：红绿状态同时用深浅/数值/形状区分，不只靠颜色。
- **【修正前文假设】** 上条"热量环 = 安全绿/接近橙/超出红"只对**减重**成立。环的语义/配色/文案必须由目标参数化，见下节。

## 目标驱动的呈现层（goalProfile）【已锁定 2026-06-05】
背景：引导可多选目标（减重/维持/增重/增肌/改善膳食/规划餐饮）。**数据层不变**（摄入/目标/营养素/体重/活动都照旧），变的只是**语义、配色阈值、文案、谁当 hero**。用一个 `goalProfile` 配置驱动同一套卡片骨架渲染——加目标只改配置，不新建页面（与"内容/呈现解耦""共用 Dashboard 骨架"两条硬原则一致）。

### 热量环有三种模式（核心，不是一种）
| 模式 | 适用目标 | target 含义 | 配色逻辑 | 中心文案 |
|---|---|---|---|---|
| **deficit（缺口）** | 减重 | 上限/预算 | 未满=绿(安全)，接近=橙，超=红 | "还可摄入 610" / 超出时"超出 130" |
| **goal-fill（达成）** | 增重 / 增肌 | 要达成的下限/目标 | 未达=琥珀(鼓励多吃)，达标=绿，略超=绿/温和 | "还需摄入 610 达标" |
| **band（区间）** | 维持 / 改善膳食 | 一个区间(带状) | 区间内=绿，偏低或偏高=琥珀 | "在区间内 ✓" / "距区间还差 …" |

要点：减重是"别填满"，增重是"要填满"，维持是"卡在中间"——颜色阈值与文案相反，不能复用同一套。无障碍：三态仍同时用形状/数值区分。

### 各模块随目标的差异
- **体重趋势**：减重 = 向下↓为好、目标线在下方；增重/增肌 = **向上↑为好、目标线在上方**；维持 = 平稳 ±0.x 为好；改善膳食/规划餐饮 = 体重非重点，**收起或仅作参考**。文案里"趋势向下""减重节奏"等措辞必须按方向取。
- **三大营养素**：增肌 = **蛋白质当主角**（更高目标、置顶/单独环）；减重 = 关注总量；改善膳食 = 比例均衡为核心 + 纤维/糖/钠提醒。
- **首页 hero**：减重/增重/增肌/维持 = 热量环（语义不同）；**改善膳食/规划餐饮可把 hero 换成"今日均衡度 / 三餐完成度"**，热量退为次要（这点最易被忽略——它不是体重 ± 目标）。
- **"我的"页**：随目标改标识与目标项。减重"减重中 · 目标 66kg · -0.4kg/周"；增肌"增肌中 · 目标 70kg · +0.25kg/周 · 蛋白 140g"；改善膳食**无体重目标** → "均衡优先 / 营养目标 / 三餐结构"。
- **引导命名档位**：减重="每周减 X"；增重="每周增 X"；改善膳食/规划餐饮无此档，换"三餐结构/偏好"。

### goalProfile 配置形状（示意）
`goal → { ringMode: deficit|goal-fill|band, colorThresholds, copySet, heroMetric, weightDirection: down|up|flat|none, macroEmphasis }`。各组件（CalorieRing / MacroBars / WeightTrend / MeScreen / 引导结尾）读它渲染。

### 多目标（可组合选）
**主目标定调**（决定 hero 指标 + 颜色语义），次目标做附加层/卡片。例：增肌+减脂(recomp) → 体重维持/微降 + 蛋白质达标 双指标并列，不硬塞进减重那套。v1 主目标在引导里让用户指定一个为主。

### v1 边界提醒（待最终确认）
方案战略默认是"体重管理"主打。两种走法二选一：(A) v1 收紧到 **减重 + 维持**，增重/增肌/改善膳食做轻量适配（仅换 goalProfile，不深做）；(B) 现在就把 goalProfile 三模式做扎实。**当前倾向 A**：先稳住减重/维持闭环，其余目标用同一配置层轻量覆盖，避免 v1 膨胀。

  - **餐次占位槽**（借鉴 MFP/Lifesum，今日页专属）：预排早/午/晚/加餐空槽，每槽显示"推荐 kcal 区间 + ➕添加"。空槽既撑起页面（解决当天记录稀疏显空），又是"去记录"的钩子。**不用于历史日记**（不会补几天前的餐）。

  - 列表视图：按天分组，**分组头做"厚"**（日期 + 当天总热量 + 状态色 + 三大营养素迷你条 + 当天缩略图小排），即使一天两三条也信息饱满；每行左侧**统一小缩略图（约 44–56pt，照片→品类图标→占位 fallback）** + 餐次/食物名 + 关键指标 + 状态色 + 进入箭头；一餐多图时缩略图加叠角/数字标记，点进详情展开。列表行距比首页紧凑。

- **我的 (Me)**：目标与预算、健康关注项、提醒、HealthKit、Widget 配置、订阅、设置。

## 添加 / 快速记录（"+" 完整逻辑）

### 入口按钮
- 底栏中间 **Z 轴层叠浮起的圆形"+"**（同基线、不凸顶边、阴影/高程 + 区分填充叠在栏上，读作动作非第 5 tab）。
- **点击** → 打开快速记录 sheet（见下）。**长按** → 直接记最常吃的模板一条（不开 sheet）。

### 架构：内容与呈现解耦（关键）
- **内容层**：`QuickAddView/VC`，**呈现无关**，不直接碰 `UISheetPresentationController`、不假设 morph；只收入参（初始餐次）、抛回调（`onLogged / onRequestExpand / onRequestDismiss`）。
- **呈现层**：协议 `QuickAddPresenter`，两实现——`SystemSheetPresenter`（系统 detents + 横条 + 滚动展开）与 `CustomMorphPresenter`（Container Transform + 自定义手势）。用 **feature flag 运行时切换**，内容零改。
- 契约取两者**公共集**（present / dismiss / 展开全屏 / "记录完成" / 两档位）；自定义独有手感（morph 起始帧、跟手参数）只活在 CustomMorph 里，系统版忽略。
- **落地顺序**：先做 **内容层 + 协议 + SystemSheetPresenter（可靠基线）**，再在 flag 后做 CustomMorph（签名升级）；自定义没打磨好就发系统版，随时可双向切换。**自定义为签名级，早期出动画原型 de-risk**。
- 注意：内容 100% 可复用；**手感/转场绑容器，切换即更换手感**（系统版无 morph，属预期）。

### 呈现形态（默认 = 自定义 Container Transform）
- **进场**：圆形"+"放大 morph 成 sheet（VC 页）；"+"图标转动着移到 sheet 角落变成 **"×"关闭按钮**。
- **退场**：反向——"×"逆旋回 tab，sheet 从上/左右收缩回圆形"+"。
- **无横条**（grabber）；可发现性/无障碍靠角落 **"×"显式关闭**兜底。

### 手势（自定义版）
- **跟手拖动**：手指不松时 sheet 1:1 跟手移动（纯拖）；**松手才执行动画**（按位移/速度阈值：回弹到某档 或 从释放点 morph 回"+"）。
- **下滑** = 关闭（半屏下滑即等于关闭，松手播放收起动画）。
- **上滑** = 展开 medium→large（全屏）。
- **全屏下，列表已到顶再下拉** = 与半屏下滑同逻辑（pan 与内部 `UIScrollView` 协调：`contentOffset.y<=0` 时转交拖动，松手才动画）。
- 系统版对应：`prefersScrollingExpandsWhenScrolledToEdge`（上滑自动 medium→large）+ `prefersGrabberVisible`（保留横条）。

### 档位与可见内容
- **medium ≈ 屏高 55–60%**，目标露 **3–4 条历史**（SE/mini 类小屏自适应减少）；紧凑 chrome（餐次 ~36pt、磁贴单行 ~88pt、行高 ~56pt）。
- **large = 全屏**。

### 第一层内容布局（不自动弹键盘）
- 顶部 **餐次分段**（按时间自动选中、可改）。
- **搜索框（默认不聚焦）**；**点搜索框 → sheet 自动展开 large + 弹键盘**，列表平滑变搜索结果（空 query = 常吃 + 历史；有字 = 结果）。新用户/无模板可**自适应首次自动聚焦**。
- **常吃 / 最近 横滑磁贴**（一键记，最高频路径）。
- **历史列表**（之前吃过若干条）。
- **底部常驻工具栏**：**拍照 / 相册 / 扫码**（docked 在底部，键盘弹起时浮其上方、键盘收起仍钉底部，**滚动时不消失**）。语音后置。

### 记录方式与下游
- **拍照 / 相册 / 扫码** → 全屏相机/选择器 → **第二层确认编辑页**。
- **搜索命中标准食物 / 点常吃模板** → 可在 sheet 内直接记完。
- 搜索数据源分层（见「关键技术选型」）：个人库 → 营养库（西式商业 API + 中式数据集）→ 条码 → AI 自由文本解析 → 手动兜底。

### 第二层：确认编辑页（仅拍照/搜索/扫码需核对时升级全屏）
- 多食物条目，各带 **份量 / 热量 / 关键指标 / 来源标签 / 置信度**；**低置信度提示"建议确认份量"**；全部**可编辑**，缺失值显示"暂无可靠数据"不用 0。
- 底部：总计 + **对今日预算影响** + 保存 / 存为常吃模板 / 手动加一项。

### 记录完成
- 保存后 **toast + 热量环动一下**，**返回原所在页面**，不强制跳转。
- 改过的条目 `status→edited`、来源可转 `user_custom`，可提示存为常吃模板。

8. 目标设定 + 平滑体重趋势 + 温和鼓励/达成恭喜页。

## 健康关注层边界（硬性原则，合规护栏）【已锁定 2026-06-05】
范围：健康关注层**只做 指标追踪 + 科普提醒 + 免责声明**，不诊断、不治疗、不预测医学数值（血糖/血脂/尿酸等，除非用户手动输入或接入 CGM）。这是一道几乎零成本但挡住最大法律/合规风险的护栏（尤其先做海外，注意 SaMD 认定）。

界面体现（同一卡片骨架内，非独立页面）：
- **一次性免责弹卡**：引导勾选健康关注项后出现，说明"仅供参考、不提供医疗诊断/治疗建议、请遵医嘱"。
- **健康关注卡**：首页一张带状态色（绿/橙/红）的指标条，如"今日碳水 168/210g ●橙"，下方一句轻提示。
- **食物确认页软标签**：碳水/钠偏高时挂"碳水较高"软标签 + 一句轻提示，不报警不恐吓。
- **ⓘ 科普弹层**：指标旁小图标，点开才显示科普（含来源 + "仅供科普参考"），放二级不打扰。
- **常驻免责声明**：「我的」页底部 + 健康关注设置页固定一行小字。

合规措辞模板（句式红线）：
- ✅ 允许："建议留意…份量""可考虑…""今日钠偏高，晚餐可清淡些"。
- ❌ 禁止："糖尿病不能吃这个""会让你血糖升到 X""按这样吃能治疗/控制血压"。
- 日报建议由规则层算出、AI 只润色，**严禁预测医学数值或给治疗方案**。

## 数据模型（吸收自对比方案，骨架直接复用）
核心实体与关键约束：
- **UserProfile**：年龄/性别/身高/体重/活动水平/目标(多选)/健康关注项/目标体重/单位。
- **DailyTargets**：每日预算与关注指标，每项用 `TargetRange { min?, target?, max?, source }`。
  - `target` 用于"希望达到"(蛋白质/水/步数)，`max` 用于"别超太多"(热量/糖/钠/饱和脂肪)。
  - **来源优先级**：用户自定义且确认 > 权威库 > 品牌/条码库 > 相似食物估算 > 纯 AI 估算。用户手动设置永远优先于系统估算。
- **MealLog**：一次记录，含 `rawInput`(原始文字/语音/图片)、`items[]`、`totals`、`confidence`、`status: draft | confirmed | edited`。
- **FoodLogItem**：单个食物，含 `displayName / quantity / nutrition / source / confidence / userEdited`。
- **NutritionFacts**：热量 + 三大营养素 + 糖/纤维/钠/饱和脂肪等；**缺失字段显示"暂无可靠数据"，绝不用 0 代替**，且不参与超标判断。

## 日报生成：规则层 + AI 文案层（双层）
- **规则层**先用明确数据算出 `fact(事实) / cause(原因) / action(动作)`，例如"脂肪超目标 28% / 晚餐炸鸡奶茶贡献最大 / 明天晚餐换蒸煮蛋白"。
- **AI 层**只把结构化结果翻译成自然、友好的话术，**不承担医学判断**。
- 健康关注项措辞受限：只能"建议留意碳水/钠"，不能"你应该如何治疗"。

## 置信度与来源标注（建立信任的关键）
- 每条食物卡显示**数据来源标签 + 置信度**(高/中/低)。
- 低置信度触发"建议确认份量"：图片含混合菜/汤/酱料/遮挡、无法判断份量、数据库无明确匹配、关键指标缺失时。
- 确认/修改后：`status→edited`、`userEdited→true`、来源可转 `user_custom`，并提示"保存为常吃模板"。

## HealthKit 细节与边界
- **第一版只读不写**：步数、活动能量、训练、体重；营养数据先存 App 内，待流程稳定后再写入(且只写用户确认过的记录)。
- `activeEnergyBurned` **不含基础代谢**；**不要把静息代谢加进"可吃额度"**(否则用户误以为躺着也能多吃)。
- **不鼓励补偿性进食**：消耗高时不说"你可以多吃 400 kcal"，改说"如饿可优先补蛋白质和高纤维"。
- 权限**分场景请求**：说明价值后再弹系统授权，不开屏全要；心率/睡眠/营养写入暂不请求。
- 体重用 7 日平均/趋势，单日上升不做负反馈。

## 成功指标 KPI
- **留存**：首日完成首次记录率、连续 3 天记录率、常吃模板创建率。
- **信任**：AI 识别确认率、低置信度修正率、手动调整营养值比例、日报建议采纳率。
- **目标**：每周≥5 天有记录用户比例、关键指标达标天数、体重趋势录入率、HealthKit 授权率。

### Upsell / 付费对比呈现规范
原则：**对比卖的是"深度/省力"，不是"精度"**；只对比能稳定兑现的能力（数据库深度、规则洞察、省时），不对比"AI 精度"。
- 适合做左右对比/锁定预览的位置：
  - **食物详情"深度分析"**：免费=名称+热量+基础营养素；VIP=完整营养拆解 + 健康关注指标 + 来源/置信度 + 改进建议（靠 DB+规则，可靠）。
  - **趋势/周报"AI 洞察"**：免费=数字图表；VIP=洞察 + 改进建议（规则层算事实、AI 润色）。
  - **"拍照即记 vs 手动输入"省力对比**：适合做付费墙主视觉，卖省力、不涉精度承诺，最安全。
- 不适合/高风险：暗示"AI 给精确权威数字"的对比（自打脸 + 健康宣称风险）；把核心记录/每日 Dashboard 锁进付费墙（杀留存）；故意把免费版做丑做残（dark pattern，伤口碑/审核风险）。
- 做法：**上下文触发**（点到锁定的深度分析/洞察、或用完免费 AI 次数时才出）；**用用户真实数据做模糊+加锁预览**，胜过通用 mockup；时机要"挣来"（用几天后再推）；保持克制美学，显式左右对比页留给专门付费墙，不每条结果弹窗。
- 注意：右侧 VIP 内容指 **AI 分析结果**，不是 AI 生成食物图片（后者已永久砍）。
