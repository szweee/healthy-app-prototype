# 饮食运动打卡 App：产品方案与路线图

> 本文是**产品定义文档**，不是代码改动计划（设计/开发尚未开始，你说过设计"暂时不急"）。先锁定范围与取舍，后续再进入设计与实现。

## 默认战略【已锁定 2026-06-05】
- 主打人群：**减肥/体重管理**；健康指标关注作为差异化次要层；慢病做成**非医疗轻量提醒 + 免责声明**。
- 平台：**iOS 优先**（HealthKit + Apple Watch + Widget），Android 后置。
- 市场：**只做海外区，当前不计划上中国区**（可重新评估），但**产品支持中文用户**（双语 i18n + 中式食物数据）。这样省掉 ICP 备案/国内主体/国内云/国内支付/推送/医疗资质一整摊重活，同时不放弃中文用户。务必区分"**服务中文用户**（做）"与"**中国区上架/合规**（不做）"。
- 商业模式：**Freemium + 订阅**（RevenueCat）。

## 核心设计原则
- 记录要**快**（记录摩擦是这类 App 头号死因）：拍照 / 常吃模板 / 条形码 优先于语音。
- 数据要**诚实**：AI 只做"识别食物 + 估份量"，营养数值**查食物数据库**；结果一律**可编辑**，展示估算/区间而非假精确。
- 文案要**温和**：避免惩罚式红色、紧迫式施压（减肥人群对负反馈敏感，存在饮食失调风险）。
- 指标**随人群自适应**：减肥看热量+三大营养素；健康关注层看糖/钠/纤维。

## 食物视觉方案（替代 AI 实时生成）
- 不做"一食物一图"，不需自行绘制大量食物图。
- v1 方案：**品类图标集（30–50 个，按品类映射，取自 SF Symbols / Twemoji / Icons8 等）+ 用户真实照片**（拍照即用真图，无图则用品类图标）。
- 包装食品走条形码时可用 **Open Food Facts 自带商品图**。
- 想要统一插画风时，后期**一次性生成 30–50 个品类插画固定复用**（与"运行时实时生成假图"区别开，前者可控、不持续烧钱）。

### 图标匹配机制：品类兜底 + 三层 fallback
- 不按"食物名查 emoji"（emoji 非为食物分类设计，可乐/奶茶/螺蛳粉等大量食物无对应 emoji）。
- 走 **食物 → 品类 → 品类图标**：品类是自己掌控的固定集合（30–50 个），每个品类预先绑定一个一定存在的图标，永不"找不到"。
- 三层 fallback：
  1. **常见食物关键词表**（可选，几百条，命中用更贴切图标，如 可乐→🥤、咖啡→☕、奶茶→🧋）。
  2. **品类图标表**（核心，必有）：未命中关键词则用数据库给出的品类对应固定图标。
  3. **终极默认**：连品类都识别不出，用中性占位图（如 🍽️ / 灰色餐盘图标）。
- 因最终都收敛到固定品类图标，**风格天然统一**（顺带解决早期担心的"图片风格乱"问题）。
- 注意 emoji 跨系统渲染样式不一致；若要视觉统一，用 **Twemoji 或自有品类图标资源**替代系统 emoji，机制相同。

## 明确砍掉 / 后置的点（守住"不四不像"）
- 永久砍：**运行时按每条记录实时 AI 生成食物图片**（无信息价值、烧钱、风格不一致问题的根源；改用上方品类图标 + 真实照片方案）。
- 砍：**月度热量上限进度条**（改用本周平均 / 7 天滚动趋势）。
- 砍：**精确减重预测、从照片预测血糖/升糖**（不准 + 打脸 + 合规风险；改为展示"能量缺口"和"平滑体重趋势"）。
- 后置：**社交/排名/点赞点粑粑**（对减肥人群有害、对慢病涉隐私；真做也只做好友私密圈 + opt-in，不做公开榜）。
- 后置：**日历双指缩放切换简洁/堆叠/详细**（炫技、成本高；先用 周/月/年 + 热力图）。
- 后置：图表自选样式、语音输入、多市场差异化。
- **砍：食谱 / Recipes（及餐单规划）**——内容产品、需持续运营、范围陷阱、不服务核心闭环；维持"不做食谱/餐单"既定取舍，v1 不做、不做 tab（远期可考虑精选/合作内容）。

## 关键技术选型
- 数据获取：**HealthKit**（主动消耗能量、步数、训练、心率、体重、睡眠）。
- 食物识别：视觉/多模态大模型识别食物与份量 → 映射到**食物数据库**取营养值。
- **食物搜索：分层合并搜**（按相关性优先级）：① 用户个人库/常吃/最近（本地优先，即时）→ ② 营养数据库（西式/品牌用商业 API 如 Nutritionix/Edamam/FatSecret）+ **中式食物成分数据集** → ③ 条码库（Open Food Facts，带商品图）→ ④ **AI 自由文本解析**（把整句拆成"食物+份量"再匹配，**跨语言兜底、中文用户尤其依赖此层**）→ ⑤ 手动添加自定义食物（存进个人库）。
- **双语 i18n（中英）从第一天就做**：UI + 搜索均支持中文（事后回改成本高）。中式混合菜估算更难，靠"结果可编辑 + 常吃模板"兜底，不承诺精确。
- 食物数据架构：不每次按键直打原始库；用**商业 API** 或把开源数据（USDA + Open Food Facts + 中式数据集）**预灌自建搜索索引**。v1 先用商业 API + 中式数据集快速上线，量大再自建索引控成本。
- 热量目标：**Mifflin-St Jeor 算 BMR → ×活动系数得 TDEE → 减肥制造 300–500 kcal/日缺口**。
- 体重趋势：**加权移动平均平滑**（参考 Happy Scale / Libra），用趋势代替预测。
- 订阅：**RevenueCat + Apple IAP**。
- 设计→代码：**Figma（含 Figma-Cursor MCP）出设计 → Cursor 生成 SwiftUI**；早期可用 v0 / Galileo 快速原型。
- **快速记录架构**：呈现无关的内容组件 + `QuickAddPresenter` 协议（`SystemSheet` / `CustomMorph` 两实现）+ feature flag；契约取两者公共集，系统版作可靠基线、自定义 Container Transform 藏 flag 后，可双向切换；自定义为签名级、早期出动画原型 de-risk。详见「添加 / 快速记录（"+" 完整逻辑）」。
- **食物数据源**：详见下方「食物数据源选型（v1）」一节。

## 食物数据源选型（v1）

核心结论：**v1 海外数据授权成本 ≈ 0**（FatSecret Premier Free + USDA + Open Food Facts 全免费/仅署名），真正花钱的是 **AI 推理** 和**自建索引的基础设施**。

### 分层数据栈（对齐「分层合并搜」）
| 层 | 来源 | 角色 | 成本/授权 |
|---|---|---|---|
| ① 个人库 | 本地（常吃/最近/自定义） | 即时、最高优先 | 自有 |
| ② 自建索引 | **USDA FoodData Central**（公有领域）+ **Open Food Facts**（ODbL）预灌进 Meilisearch/Typesense | 通用食物 + 控延迟控成本 | 免费（署名 + share-alike） |
| ③ 商用层 | **FatSecret Premier Free** | 美区全量 + 条码 + autocomplete + 食物图 | 免费（<$1M 营收/融资，需署名） |
| ④ 条码 | **Open Food Facts** | 包装食品 + 商品图（CC BY-SA） | 免费（署名） |
| ⑤ AI 文本/图像解析 | 多模态 LLM | 拆"食物+份量" → 映射回 ②③ 取营养值；跨菜系/中文长尾兜底 | 按量（LLM 调用） |
| ⑥ 手动自定义 | 用户输入 | 回流个人库/共享库 | 自有 |

### 拍照识别（已定 = 方案 A）
- **LLM 当识别器 + 自建库当真值**：视觉模型识别"食物名 + 份量估计" → 映射 ②③ 数据库取营养值。**与 ⑤ 文本解析共用一套管线**，跨菜系灵活、不锁厂商。
- 不用 FatSecret/Edamam 的 Vision add-on（按调用收费 + 锁厂商 + 中餐覆盖弱）。
- 结果一律可编辑、显示置信度与来源（沿用既定"来源标签 + 置信度"）。

### 中文食物数据（已定 = 方案 A）
- **人工精选 ~500–1000 条最常见中餐/饮品种子集**灌进自建库（参考公开成分资料整理，注意《中国食物成分表》有版权、不直接拷贝其库）。
- **长尾靠 ⑤ AI 拆解**（菜 → 食材 → USDA 值）+ **用户自定义回流**。
- **不承诺混合菜精确**，靠"结果可编辑 + 常吃模板"兜底。
- 不付费授权中式成分库（v1 太贵太慢，可 v2 重估）。

### 合规要点（锁进方案）
- **署名**：设置/关于页放"数据来源"页，列 FatSecret / Open Food Facts / USDA；每条记录沿用"来源标签"。
- **Open Food Facts**：衍生库 share-alike、商品图 CC BY-SA 均需署名。
- **缓存权**：FatSecret Premier Free 允许建自有日记/缓存；Edamam 低价层缓存受限——若仅作备用需先确认条款。
- **迁移预案**：营收/融资超 $1M 或需**非美区数据**时，迁移到付费 FatSecret Premier（初创 5 折）或自建索引扩容；接口层抽象好，换源不动上层。

### 备用/可选
- **Edamam Food Database**（$14–$69/月，90 万食物 + 68 万条码）作 FatSecret 的备用或补充；低价层注意缓存限制。
- **Nutritionix** 当前 $499+/月、无免费层，**v1 不用**。

## 关键技术 Spike（可行性验证）

三个高风险点，**写代码前先各做一个 time-box 的最小验证**，定"能不能做 + 怎么验 + 不过关的兜底"。优先级：① HealthKit（最确定）→ ② 拍照识别（最不确定、决定卖点）→ ③ 体重趋势（中等）。

### Spike 1 — HealthKit 读取边界
- **能不能做**：能。读取用 `HKHealthStore` 申请只读权限，按类型查询。
- **读哪些**：`stepCount`（步数）、`activeEnergyBurned`（主动消耗，**燃烧的真值来源**）、`HKWorkout`（训练类型/时长/能量）、`bodyMass`（体重）。可选：`basalEnergyBurned`（BMR，**只读不加进预算**）、`heartRate`、`sleepAnalysis`（v2）。可选回写 `dietaryEnergyConsumed`（把记录的食物写回健康 App）。
- **边界与坑**：
  - **隐私不可知**：Apple 不告知"读权限是否被拒"，被拒时查询**静默返回空**——无法区分"没授权"和"今天没数据"，**UI 必须对'无数据'优雅降级**，不能弹"请授权"误导。
  - **双重计算**：Apple Watch 的步数已计入 `activeEnergy`；若再用步数自己估热量并和 `activeEnergy` 相加会**重复计数**。规则：**有 `activeEnergy` 用它当真值，无表/无能量数据才退化到步数估算**。
  - **不灌水预算**：沿用既定原则，不把 BMR/运动消耗自动加进可吃额度（"吃回运动量"默认关）。
  - **后台更新**：`HKObserverQuery` + `enableBackgroundDelivery` 才能及时刷新。
  - **单位/多源**：用 `HKUnit` 处理 kcal/kJ、kg/lb；`bodyMass` 可能多来源（秤/手输），需去重 + 取最新 + 来源优先级。
  - **模拟器无健康数据**，必须真机（带/不带 Watch 各测）。
- **怎么验**：最小 app 申请上述 4–5 类权限 → 查"今日 activeEnergy + 步数 + 最近一次 bodyMass + 最近训练" → 打印；真机带 Watch / 不带 Watch / 拒权限 三种场景各跑一遍；验证后台投递能触发。
- **通过标准**：真机能读到今日主动消耗/步数/最新体重；拒权限/无数据时不崩不误导；燃烧总额无双重计数。
- **兜底**：拿不到 HealthKit → 步数手动/估算 + 体重手输，功能不阻断。

### Spike 2 — 拍照识别 + 查库精度（最关键，决定 AI 卖点）
- **管线**：照片 → 多模态 LLM 输出 `{食物名[], 份量估计, 置信度}` → 食物名映射营养库（USDA/FatSecret/自建）取营养值 → 可编辑确认页。
- **最弱环节 = 份量估计**：单张照片无深度参照，估"克数/份量"误差天然大。**产品对策：份量默认按'用户确认'，AI 份量只作建议**（给常见份量选项 + 可选参照物），**不自动信任份量**——这一条直接把精度风险降级（也和既定"可编辑 + 置信度"一致）。
- **怎么验（建基准集）**：收 ~50–100 张带标注食物照（西式 + 中式 + 包装混合），标注真值食物名 + 大致热量。指标：
  - **食物识别 Top-1 / Top-3 命中率**（名字对不对）。
  - **名字→库匹配命中率**（解析名能否落到正确库条目）。
  - **份量估计误差**（估计克数 vs 实际，MAE / ±X% 占比）——单独看，预期差。
  - **端到端热量误差**（最终 kcal vs 真值，落在 ±30% 内的占比）。
  - **延迟 P50/P95、单次成本**。
  - 同基准集横评 2–3 个模型（GPT-4o / Gemini / Claude）。
- **通过标准（建议）**：食物识别 Top-3 ≥ 80%；端到端热量在份量由用户确认的前提下 ±30% 内占比达标；延迟/成本可接受。
- **决策门 / 兜底**：若识别尚可但份量太差 → **走"AI 识别名字 + 用户选份量 + 查库取值"**（已是默认）；若整体识别也差 → 拍照降级为"打开确认页让用户搜/选"，照片仅作记录留存。**无论如何 AI 结果全可编辑、标置信度与来源。**

### Spike 3 — 体重趋势平滑算法选型
- **目标**：显示**诚实趋势**，不被每日水分噪声（±1–2 kg）带偏，也不做"必达 X 日"的硬预测。
- **选型**：**指数加权移动平均 EWMA**（Happy Scale / Libra 同款），半衰期约 ~10 天；**淡画原始点 + 粗画趋势线**；速率（kg/周）由趋势线在尾窗的斜率得出，配不确定区间。备选 SMA（有滞后）、线性回归斜率（算速率）、Kalman（过重，不做）。
- **怎么验**：用真实/合成体重序列（注入每日噪声 + 缺测 + 离群秤读数）跑 EWMA，对比 SMA / 回归斜率：① 趋势线在噪声下是否稳定不误导；② 速率估计是否接近注入的真实斜率（容差内）；③ 缺测/单点/离群的鲁棒性（离群剔除）。
- **通过标准**：趋势线在 ±1–2 kg 噪声下视觉平稳；速率估计匹配真实斜率；缺测/离群不崩不跳。
- **展示与合规**：呈现为"近 2 周 -0.4 kg/周"这类**描述性趋势**，避免硬 ETA 预测或给"必达日期"；如给预计达成，用**区间 + 免责**（呼应健康合规边界）。

## 首次引导（借鉴 MyFitnessPal，去其冗余，压到 4 步）
核心原则：**目标先行 → 先给价值（引导末尾立刻展示每日预算）→ 功能渐进式引出 → 注册/付费/社交后置**。

当前原型支持 `?onboarding=1` 强制重走引导；完成后将 `selectedGoal`、经验分层和作息模板写入本地状态，普通刷新保留上次选择。首页与我的页应读取引导结果，而不是读取固定 mock 目标。

引导流程（每步分屏、不堆叠）：
1. **经验分层**（借鉴 Lose It）：先问"以前算过卡路里吗"→ 决定后续科普深度。铁律：**问了必须跟进**——选"没算过"的给新手解释 + 更低门槛首次记录；选"算过"的跳过科普直接进阶。（Lose It 的错就是问了却不跟进，把"怎么算"丢给用户，导致新手困惑。）
2. **目标多选**（减重 / 维持 / 增重 / 增肌 / 改善膳食 / 规划餐饮…，可组合）→ 决定首页主指标预置。
3. **基础信息**：年龄、性别、身高、体重、活动水平（分屏采集）。
4. **推荐目标确认 + 目标速度选择（启动页必须做）**：先采集当前体重 / 目标体重，再让用户在系统推荐的周期与速度中选择，不能让首页 badge 写死。"减重中 · 每周 -0.5kg"这类文案来自这里的 `targetPace`。
   - 推荐用**命名档位**呈现（如 放松 / 稳定 / 积极 / 高强度，借鉴 Lose It），每档明确写"每天 X kcal + 每周减/增 X kg + 预计约 X 周"，权衡一目了然；BMR/TDEE 计算，附保守/积极/手动选项。
   - 减重默认推荐 **稳定：约 -0.5kg/周**；放松约 -0.25kg/周；积极约 -0.75kg/周；高强度接近 -1.0kg/周时必须给安全提示，不默认推荐。过激档位（每周 >0.7–1kg 或热量过低）给**安全护栏警示**，不让无脑选最猛。
   - 增重/增肌同理，但默认更保守：稳定约 +0.25kg/周；积极约 +0.5kg/周；更快时提示脂肪增加概率更高，要求训练和蛋白质更稳定，不默认推荐。
   - 用户可以表达"1 个月减/加 5kg"或"3 个月减/加 5kg"，系统要换算成每周速度并判断安全性。若速度偏激进（如 1 个月减 5kg ≈ -1.25kg/周），不要直接通过；提示"这个速度偏激进，可能更难坚持，建议改为 2–3 个月或选择稳定方案"，并给"改为稳定方案 / 调整目标日期"。
   - 维持目标不显示每周减/增速度，改为"维持区间"与体重波动范围。
   - 目标速度、目标日期、每日预算和首页 badge 必须联动；用户后续在"我的目标"修改速度时，首页 badge 和热量目标同步更新。
   → **立刻展示"我的每日预算"**（MFP 最关键的转化设计，先给价值）。
5. **记录习惯**：用餐提醒时间 + HealthKit 授权（带场景说明后再弹系统授权）。

引导结尾（修掉 Lose It "算完没人教"的坑，并立住差异化）：
- **一句安心话术**：核心卖点是"你不用自己数卡路里"——拍照/输入/选模板，App 帮你估算，随时可改。文案示例："不用自己算卡路里——拍张照或输入吃了什么，我们帮你估算，你随时能改。"
- **引导式首次记录**（借鉴 MFP guided first entry）：引导一结束立刻带用户记第一条，既教会用法又完成激活，新手不会卡在"那现在干嘛"。

目标 → 主指标的"轻分支"映射（共用同一引擎，仅换主指标/文案/卡片预置，**不衍生独立重功能**）：
- 减重 → 热量缺口、净摄入、体重趋势。
- 增重/增肌 → 总热量盈余、蛋白质、训练日。
- 改善膳食 → 三大营养素均衡、纤维/糖/钠提醒，弱化热量数字。
- 规划餐饮 → 侧重常吃模板/提前安排（v1 不做真正的餐单规划/食谱功能）。

明确不抄 MFP 的点：过长引导漏斗、采集 location、管理压力/冥想类目标、引导中强推付费/注册墙、"如何得知本 App"归因问题。注册/付费墙后置到**首次记录完成之后**，降低首跳流失。

教育/价值主张插页（借鉴 Yazio，**总量 2–3 屏封顶**，避免 Noom 式超长说服漏斗）：
- ✅ **溜溜球科普屏**：讲"过度节食→反弹+伤健康"，为我们的"温和缺口/安全护栏"背书。**红线：引用研究必须真实可核对，不摆假权威 logo。**
- ✅ **不忌口/定制价值主张屏**：传达"无需忌口、不用复杂规则、按你的生活方式定制"，契合低摩擦 + 不焦虑（视觉自有，不照搬 Yazio 配色）。
- ⚠️ **健康改善屏须去疗效化**：**禁止承诺具体疾病风险下降**（如"糖尿病/高血压/胆固醇降低"——违反健康关注层合规红线，海外 FTC/SaMD 高风险）。改为非疗效弱关联措辞，如"坚持均衡饮食与稳定体重，通常让你状态更好"；不点名疾病数值。此屏改造后**可选**，否则砍。
- 插页放在采集基础信息之后，让其显得"为你定制"；纯展示点"继续"即可，不增加输入负担。

## UI / 视觉设计原则（借鉴 Lifesum 的信息层级，坚持自有克制风格）
最高准则（用户原话）：**简约易用、布局清晰、美观大气**。

- **一屏一焦点**：首页中央就是热量预算环（Consumed / Remaining / Burned，**Remaining 最大**、行动导向），并**随预算状态变色**（安全绿 / 接近橙 / 超出红）。环下紧跟三大营养素条。
- **每餐给"推荐 kcal 区间"**（借鉴 Lifesum，如早餐 437–612），用区间不用死数字，顺带回答"该吃多少"。
- **首页只展示结果与下一步，不常驻展示推导**：BMR/TDEE/热量缺口/盈余属于信任解释层，放在热量目标旁的 `ⓘ` 说明弹层；首页默认不放整张"今日目标怎么算"卡。
- **首页下一步建议优先于堆指标**：热量环下方放一条规则模板生成的行动建议，如"若晚些饿，加餐建议 120–210 kcal，蛋白质还差 23g。可选无糖酸奶、鸡蛋、牛奶或豆腐。"不要只写泛泛的"状态不错"。
- **蛋白质可被单独拎出来**：三大营养素条仍展示碳水/蛋白质/脂肪总览，但首页三列统计中可把中间位给"蛋白质还差 Xg"，因为它对减重保肌肉、饱腹感和增肌最有行动价值；碳水/脂肪不默认抬到同层，避免首页变成营养报表。
- **卡片化 + 充足留白 + 大字号**，弱化营养术语，强调"还差多少 / 下一步"。
- **克制配色**：单一主强调色 + 中性灰底、轻渐变（不照搬 Lifesum 浓绿渐变顶栏）；**深色模式一等公民**。
- **人群预置 + 可编辑卡片**：喝水 / 蔬果 / 健康指标等做成**可开关卡片**，按人群默认、用户可增删排序，不默认全堆上。喝水可作为可选卡片；睡眠更适合做洞察提示；心率不默认进首页，避免产品变成泛健康仪表盘或触发医疗化解读。
- **【硬性原则】全 App 共用一套卡片化 Dashboard 骨架**（热量环 → 营养素条 → 餐次 → 活动 → Tab）。人群/健康关注**只改卡片的显隐、排序与主指标，绝不新建独立页面布局**。食物确认页的健康提示也是同页条件元素，非独立页面。避免"每类人一套页面"导致的设计/工作量膨胀。
- **正向微文案**：借鉴 Lifesum "Daily Wins" 式鼓励，而非超标惩罚式红字。
- **无障碍**：红绿状态同时用深浅/数值/形状区分，不只靠颜色。
- **【修正前文假设】** 上条"热量环 = 安全绿/接近橙/超出红"只对**减重**成立。环的语义/配色/文案必须由目标参数化，见下节。

## 目标驱动的呈现层（goalProfile）【已锁定 2026-06-05】
背景：引导可多选目标（减重/维持/增重/增肌/改善膳食/规划餐饮）。**数据层不变**（摄入/目标/营养素/体重/活动都照旧），变的只是**语义、配色阈值、文案、谁当 hero**。用一个 `goalProfile` 配置驱动同一套卡片骨架渲染——加目标只改配置，不新建页面（与"内容/呈现解耦""共用 Dashboard 骨架"两条硬原则一致）。

### 热量环有三种模式（核心，不是一种）
| 模式 | 适用目标 | target 含义 | 配色逻辑 | 中心文案 |
|---|---|---|---|---|
| **deficit（缺口）** | 减重 | 上限/预算 | 未满=绿(安全)，接近=橙，超=红 | "还可摄入 610" / 超出时"超出 130" |
| **goal-fill（达成）** | 增重 / 增肌 | 要达成的下限/目标 | 未达=琥珀(鼓励多吃)，达标=绿，略超=绿/温和 | "还需摄入 610 达标" |
| **band（区间）** | 维持 / 改善膳食 | 一个区间(带状) | 区间内=绿，偏低或偏高=琥珀 | "在区间内 ✓" / "距区间还差 …" |

要点：减重是"别填满"，增重是"要填满"，维持是"卡在中间"——颜色阈值与文案相反，不能复用同一套。无障碍：三态仍同时用形状/数值区分。

### 各模块随目标的差异
- **体重趋势**：减重 = 向下↓为好、目标线在下方；增重/增肌 = **向上↑为好、目标线在上方**；维持 = 平稳 ±0.x 为好；改善膳食/规划餐饮 = 体重非重点，**收起或仅作参考**。文案里"趋势向下""减重节奏"等措辞必须按方向取。
- **三大营养素**：增肌 = **蛋白质当主角**（更高目标、置顶/单独环）；减重 = 关注总量；改善膳食 = 比例均衡为核心 + 纤维/糖/钠提醒。
- **首页 hero**：减重/增重/增肌/维持 = 热量环（语义不同）；**改善膳食/规划餐饮可把 hero 换成"今日均衡度 / 三餐完成度"**，热量退为次要（这点最易被忽略——它不是体重 ± 目标）。
- **首页只显示当前主目标**：减重/维持/增肌切换只用于原型评审；真实产品里用户在引导或"我的目标"里选择一个主目标，首页不放三目标切换控件。
- **首页右上角目标 badge 不写死**：例如"减重中 · 每周 -0.5kg"来自首次引导/我的目标中的 `targetPaceKgPerWeek` 和 `goalProfile`。减重显示每周负值，增重/增肌显示每周正值，维持显示目标区间；点击可进入目标说明/调整页。
- **下一餐建议按目标换语义**：减重 = 控制总量 + 保蛋白；维持 = 稳定区间 + 不焦虑；增肌 = 吃够总量 + 蛋白质 + 训练日碳水。建议由规则模板生成，AI 最多润色，不改变事实。
- **"我的"页**：随目标改标识与目标项。减重"减重中 · 目标 66kg · -0.4kg/周"；增肌"增肌中 · 目标 70kg · +0.25kg/周 · 蛋白 140g"；改善膳食**无体重目标** → "均衡优先 / 营养目标 / 三餐结构"。
- **引导命名档位**：减重="每周减 X"；增重="每周增 X"；改善膳食/规划餐饮无此档，换"三餐结构/偏好"。

### goalProfile 配置形状（示意）
`goal → { ringMode: deficit|goal-fill|band, colorThresholds, copySet, heroMetric, weightDirection: down|up|flat|none, macroEmphasis, targetPaceKgPerWeek, targetDate, badgeCopy }`。各组件（CalorieRing / MacroBars / WeightTrend / MeScreen / 引导结尾 / 首页 badge）读它渲染。

### 多目标（可组合选）
**主目标定调**（决定 hero 指标 + 颜色语义），次目标做附加层/卡片。例：增肌+减脂(recomp) → 体重维持/微降 + 蛋白质达标 双指标并列，不硬塞进减重那套。v1 主目标在引导里让用户指定一个为主。

### v1 边界提醒（待最终确认）
方案战略默认是"体重管理"主打。两种走法二选一：(A) v1 收紧到 **减重 + 维持**，增重/增肌/改善膳食做轻量适配（仅换 goalProfile，不深做）；(B) 现在就把 goalProfile 三模式做扎实。**当前倾向 A**：先稳住减重/维持闭环，其余目标用同一配置层轻量覆盖，避免 v1 膨胀。

## 信息架构 / 底部导航（3 tab + 右侧悬浮"+"）
- **今日 (Home)**：落地页。热量预算环 + 三大营养素 + 今日餐次 + 活动消耗 + 可选 Daily Wins；日报做成此页的"今日小结"卡（不单开 tab）。
  - **首页不常驻日期切换控件**：今日页主任务是今天结果与下一步记录，不做显式日历导航。可保留左右滑动回看最近日期；回看时标题下轻提示"正在回看历史记录"，并在同一行显示"回到今天"。更具体的周/月/年时间浏览交给趋势页和历史记录页。
  - **今日快捷餐次入口**（借鉴 MFP/Lifesum，今日页专属）：预排早/午/晚/加餐入口，每项显示状态（已记 / 补记 / 推荐 / 随时 / kcal 区间）。入口应放在今日目标与活动概览之后，靠近拇指可达区域，避免首页顶部占满导致记录入口够不着。**不用于历史日记**（历史补记从日期切换/记录详情进入）。
  - **快捷餐次推荐与缺口提醒分离**：推荐表示"现在最可能要记什么"，缺口提醒表示"哪餐还没记录"。例如午餐窗口已过且午餐未记、晚餐还没到时，不强行推荐午餐；显示"午餐还没记录 / 先补午餐 · 有吃再记"，午餐按钮标"补记"，加餐按钮只标"有吃再记/可选"，不要写成"推荐加餐"，避免暗示用户应该加餐。
  - **餐次时间可调但不强迫配置**：v1 默认使用系统餐次时间窗；首页快捷餐次提示里保留轻入口 **"调整餐次时间"**，当用户觉得判断不准时可以现场修改，不需要一开始就知道设置藏在哪里。
  - **今日记录不常驻展开列表**：首页底部只保留一行记录摘要入口，如"今日已记录 1 餐 / 早餐 · 330 kcal / 查看全部 ›"；无记录时显示"今日还没有饮食记录 / 去记录 ›"。完整照片、餐次、编辑和删除进入记录详情/历史页。
  - **今日活动卡**：首页只展示轻量概览，如"今日活动 320 kcal / 步行 210 · 训练 110"；点击进入活动详情二级页。不要写"活动单独记录"这类内部逻辑话术。
  - **活动详情二级页**：展示总活动消耗、来源明细（步行与日常活动 / Workout / 手动记录）、HealthKit 读取说明、未同步空状态、轻量补录入口。详情页解释"健康同步为主，手动记录单独列出，避免重复计算"；不要在详情页常驻大块补录表单，补录入口文案可为"没有同步到运动？补录一项 ›"，点击后进入 QuickAdd 运动模式或运动补录 sheet。
- **趋势 (Progress)**：所有"回看/分析"集中地。趋势页不只是图表页，要回答 **发生了什么、为什么、下一步做什么**；首页负责今日建议，趋势页负责周/月/年维度的复盘和下钻。**结构 = 顶部时间档（周/月/年）+ 当前周期轻提示 + 概览卡 + 下钻详情**，复用卡片化骨架，不在本页铺满大图：
  - **周期浏览交互**：右上角保留 周/月/年 segmented control；不再额外放一张厚重的周期导航卡。当前周期用标题下轻文本体现，如"2026 年 5 月"、"本周"、"2026 年"；偏移时同一行出现"回到当前"。内容区支持左右滑：选择周时左/右滑按周切换，选择月时按月切换，选择年时按年切换。
  - **本期小结卡（报告）置顶**：一句结论 + 1–2 条建议（周报/月报即此卡，"结论→证据"逻辑）。
  - **卡片顺序建议**：本期小结 → 概览指标 → 体重趋势 → 热量摄入趋势 → 记录完整度 → 活动概览。
  - **体重趋势卡**（迷你趋势线 + 距目标差）→ 点进体重详情。
  - **能量趋势卡**（摄入 vs 消耗 / 净值迷你柱）→ 点进能量分析。
  - **记录热力图卡**（GitHub 式方格）→ 点进全屏热力图 + streak。
  - （可选）营养结构卡。
  - 每张卡只放一眼看懂的缩略图，深度内容一律下钻二级页；不要把趋势页做成大报告堆叠，**v1 卡片 4–5 张封顶**，避免又一个臃肿页。
- **底部导航视觉**：底栏做成类似趋势页 周/月/年 的小型 segmented control，而不是铺满宽度的大 tab bar。`今日 / 趋势 / 我的` 放在一枚窄胶囊里，选中态是内层小圆角，和外层胶囊留少量空隙；tab 胶囊本身需要整体阴影/毛玻璃，避免和页面底部内容重叠时识别不清。
- **➕ 右侧独立悬浮记录按钮**：底栏左侧收敛为 3 个一级 tab（今日 / 趋势 / 我的），右侧保留独立圆形"+"动作按钮；`tab 胶囊 + +` 作为一个整体居中，而不是 tab 靠左、加号孤立靠右。`+` 与 tab 胶囊同基线、尺寸接近、保留间距，靠阴影/高程 + 区分填充读作"全局记录动作"，不是第 4 个 tab。点击 → 快速记录。**完整逻辑见下方「添加 / 快速记录（"+" 完整逻辑）」一节。** `+` 是统一记录入口，默认进入饮食；运动作为同一 sheet 内的次级模式，不另开一级 tab；加号展开/收起的 Container Transform 从右侧悬浮按钮发起。
- **一级 tab 切换动画**：保留轻微上移动画（新页面从下方小幅上移淡入，旧页面小幅上移淡出），但不要使用会先卸载旧页面再等待新页面进入的 `wait` 队列式转场；快速连续切 tab 时不能出现空白页。实现上应让新旧页面在同一容器内短暂交接，或采用不会清空内容的同步入场动画。
- **记录 / 历史（原"日记"降级为二级能力）**：跨天完整记录流，**可浏览、可编辑历史记录**（"已存数据可改"落点），但不再默认占一级 tab；优先从首页左右滑回看后的记录摘要、餐次"查看记录"、趋势页 Heatmap / IntakeTrend 下钻进入。当前原型默认打开**当天记录详情**，而不是先进入相册月历。
  - 当天记录详情：顶部返回 + 日期/来源摘要 + 添加/补记入口；中间展示总摄入、已记录餐数、关键状态；下方是餐次/食物列表，每行有缩略图、餐次、时间、来源、热量，后续可点进编辑。
  - 空记录状态：显示"这天还没有记录" + 解释为什么补记会让趋势更准 + "补记当天记录"入口。
  - 天记录详情支持左右滑切换前一天/后一天：右滑看前一天，左滑看后一天；非今天时顶部轻文本显示"回到今天"。滑到空记录日时显示补记入口，不额外放厚重日期导航。
  - 月记录详情支持左右滑切换上月/下月：右滑看上月，左滑看下月；非当前月时顶部轻文本显示"回到本月"。若用户在"照片"视图滑动月份，应保持照片视图，不强制切回列表。
  - 跨天浏览：先由首页轻量左右滑、趋势页周/月/年、热力图和摄入柱下钻承接；不在一级底栏放独立"日记"。
  - 当天照片入口：当天记录详情默认仍是餐次列表；若当天有照片记录，右上角显示轻入口 **"照片 N ›"**，点开只看当天照片墙/叠卡，编辑仍回到记录列表。
  - 月度照片入口：从趋势页年/月度记录或"查看月度记录"进入时，可在记录页顶部提供 **"列表 / 照片"** segmented 切换；照片视图展示本月照片墙/相册月历，用于回忆和复盘。
  - 相册月历/照片墙不作为一级 tab，也不作为当天记录默认页。它是记录页内的增强视图：有照片、有月度上下文、或用户主动切到照片时才展示，避免产品气质偏向相册/手账。
  - 与趋势热力图分工：**记录二级页=具体照片/餐次/可编辑记录，趋势热力图=抽象状态色(达标/依从度)**，不重复。
- **我的 (Me)**：目标与预算、健康关注项、提醒、HealthKit、Widget 配置、订阅、设置。

布局先按 `今日 · 趋势 · 我的` 三个一级 tab + 右侧悬浮 `+` 收敛。原"日记"不替换成新的一级 tab；历史记录降为二级页，入口从首页记录摘要、趋势下钻、活动详情和保存后的提示进入。

取舍：**不设"报告"独立 tab**（并入今日小结卡 + 趋势深度版）；**故意砍掉 Recipes / Programs 类 tab**（食谱/餐单计划 v1 不做，比 Lifesum 更清爽）；**"+"是动作而非页面**，贴合低记录摩擦。历史记录必须存在且可编辑，但不必作为一级目的地。

### 趋势页组件与下钻规则

#### 热量摄入趋势（IntakeTrend）
- 周/月视图：点击某根柱子后，展示具体日期、当天总摄入、与目标差值、当天餐次明细、主要原因、下一步建议，以及 **"查看当天记录"** 入口。解释要帮助用户定位原因，例如晚餐或加餐偏高，而不是只展示数值。
- 年视图：点击某个月后，展示月均摄入、偏离目标、记录天数、月度摘要，以及 **"查看月度记录"** 入口。
- 原型里可以用 mock 餐次演示，但正式开发必须从真实 `MealLog` 聚合；**不能按固定比例硬拆早餐/午餐/晚餐/加餐**，否则会制造假解释。
- 柱子需要是可点击控件语义，例如 `button` + `aria-label`，不要只是 `div onClick`。

#### 记录完整度（Heatmap）
- Heatmap 要支持 `range + offset`，周/月/年切换和趋势页左右滑切换周期时生成对应日期。
- 月视图用真实日历空白占位；年视图尾部跨年格子不可点击。
- 点击格子后展示：具体日期、完整度等级、记录餐数、热量概览、缺口提示。空记录时入口是 **"补记当天记录"**；有记录时入口是 **"查看当天记录"**。
- 周/月/年切换或左右滑切换周期时要重置选中状态，避免用户看到上一个周期遗留的详情。
- 完整度等级可先用规则模板：未记录 / 记录较少 / 记录一般 / 记录较多 / 记录完整。完整度不只看有没有记录，也要结合餐次数、热量、宏量营养素是否完整。
- 热力图和历史记录页分工：**热力图 = 抽象状态色，用来看依从度/完整度**；**历史记录页 = 具体照片/餐次/可编辑记录**。

#### 体重趋势（WeightTrend）
- 体重趋势应按目标解释：减重时趋势下降通常是正向，但单日上升不做负反馈；增肌/增重时体重上升不一定等于增肌，最好结合蛋白质、训练、围度/体脂估算；维持时看稳定区间，而不是越低越好。
- 体重数据来源以用户手动输入为主，可接 HealthKit 体重数据；不默认每天催称重，允许用户设置提醒。
- 数据缺失时，趋势线用已有数据平滑显示，缺测点要标识，不要硬连成"确定趋势"。

## 添加 / 快速记录（"+" 完整逻辑）

### 入口按钮
- 底栏右侧 **独立悬浮的圆形"+"**（与三 tab 胶囊同基线、有明确间距、阴影/高程 + 区分填充，读作全局记录动作而非 tab）。
- **点击** → 打开快速记录 sheet（见下）。**长按** → 直接记最常吃的模板一条（不开 sheet）。

### 架构：内容与呈现解耦（关键）
- **内容层**：`QuickAddView/VC`，**呈现无关**，不直接碰 `UISheetPresentationController`、不假设 morph；只收入参（初始餐次）、抛回调（`onLogged / onRequestExpand / onRequestDismiss`）。
- **呈现层**：协议 `QuickAddPresenter`，两实现——`SystemSheetPresenter`（系统 detents + 横条 + 滚动展开）与 `CustomMorphPresenter`（Container Transform + 自定义手势）。用 **feature flag 运行时切换**，内容零改。
- 契约取两者**公共集**（present / dismiss / 展开全屏 / "记录完成" / 两档位）；自定义独有手感（morph 起始帧、跟手参数）只活在 CustomMorph 里，系统版忽略。
- **落地顺序**：先做 **内容层 + 协议 + SystemSheetPresenter（可靠基线）**，再在 flag 后做 CustomMorph（签名升级）；自定义没打磨好就发系统版，随时可双向切换。**自定义为签名级，早期出动画原型 de-risk**。
- 注意：内容 100% 可复用；**手感/转场绑容器，切换即更换手感**（系统版无 morph，属预期）。

### 呈现形态（默认 = 自定义 Container Transform）
- **进场**：右侧圆形"+"放大 morph 成 sheet（VC 页）；"+"图标转动着移到 sheet 角落变成 **"×"关闭按钮**。
- **退场**：反向——"×"逆旋回右侧悬浮按钮，sheet 从释放位置收缩回圆形"+"。
- **无横条**（grabber）；可发现性/无障碍靠角落 **"×"显式关闭**兜底。

### 手势（自定义版）
- **跟手拖动**：手指不松时 sheet 1:1 跟手移动（纯拖）；**松手才执行动画**（按位移/速度阈值：回弹到某档 或 从释放点 morph 回"+"）。
- **下滑** = 关闭（半屏下滑即等于关闭，松手播放收起动画）。
- **上滑** = 展开 medium→large（全屏）。
- **全屏下，列表已到顶再下拉** = 与半屏下滑同逻辑（pan 与内部 `UIScrollView` 协调：`contentOffset.y<=0` 时转交拖动，松手才动画）。
- 系统版对应：`prefersScrollingExpandsWhenScrolledToEdge`（上滑自动 medium→large）+ `prefersGrabberVisible`（保留横条）。

### 档位与可见内容
- **medium ≈ 屏高 55–60%**，目标露 **3–4 条历史**（SE/mini 类小屏自适应减少）；紧凑 chrome（餐次 ~36pt、磁贴单行 ~88pt、行高 ~56pt）。
- **large = 全屏**。

### 第一层内容布局（不自动弹键盘）
- 顶部不放大标题；结构为 **关闭按钮 + 日期/时间入口 + 饮食/运动分段切换**。饮食/运动切换使用与趋势页周/月/年一致的圆角 segmented control，放右上角；默认停留在饮食，因为拍照/搜索记食物是主路径；运动用于 HealthKit 缺失、漏同步或用户主动补录时的兜底。
- **日期/时间入口**用于今天记录和历史补记：点击后显示今天 / 昨天 / 前天 / 选日期等选项。展开时应让 sheet 内内容整体向下移动，选项也用位移/高度动画出现，不要突然插入造成跳动。右侧悬浮 `+` 打开时也可选择历史日期，用于补昨天/前天的用餐和运动记录。
- 顶部 **餐次分段**（按规则自动选中、可改）。餐次选择决定拍照/搜索结果保存到早餐/午餐/晚餐/加餐。
- **半屏 medium 的核心是快速启动器，不是完整编辑页**：餐次分段下方是一行主入口 **拍照识别 / 相册 / 扫码 / 搜索**。拍照识别是主强调，其余为浅底按钮；按钮高度尽量压缩，保证半屏露出常吃/最近记录。
- **搜索默认不是一整行输入框**：半屏只显示"搜索"按钮。点击搜索时，sheet 与搜索控件应同时开始动画：sheet 展开到 large，同时搜索按钮向左延伸成搜索输入框，前面的拍照/相册/扫码按钮淡出，搜索图标顺势移动到输入框前面；不要先展开页面再让输入框从旧位置跳上去。
- **搜索收回规则**：如果用户没有输入内容，从 large 下滑回 medium 时，搜索框应收回成"搜索"按钮，拍照/相册/扫码按钮动画复原。若已有输入内容，则可保持搜索态或提醒确认，避免误丢搜索上下文。
- **餐次建议是轻量上下文，不是大卡片**：只在今天记录时显示，放在餐次分段之后、主入口按钮之前；压成一条短提示（标题 + 一句建议 + 1–2 个快捷项）。补记昨天/前天/选日期时不显示餐次建议，因为补记应按实际吃了什么记录，不用给"今天应该吃什么"的建议。
- **常吃 / 最近**：半屏可展示为横向紧凑 chips 或短列表。不要把这里命名成过重的"一键记"以免和独立快捷记录概念混淆；它在 `+` sheet 内的角色是"快速选一个常吃食物继续记录/直接记录"。真正的一键记可作为首页快捷或长按 `+` 的增强能力。
- **历史列表**（之前吃过若干条）在常吃之后展示；large 搜索态中变成搜索结果（空 query 可展示常吃 + 最近，有字则展示分层搜索结果）。

### 默认餐次推断与友好提示（实现逻辑）
- 这块大部分属于代码规则，不应只写死 UI 文案。实现上应提供类似 `inferDefaultMeal({ now, recordedMeals, lastMealTime })` 的函数，返回默认餐次、原因码和建议文案；QuickAdd 打开时用它初始化餐次和提示。
- 不要只按当前时间猜餐次，而要结合 **当前时间 + 已记录餐次 + 距离下一正餐的远近**。正餐时间窗可先用模板：早餐 05:00–10:30，午餐 11:00–14:00，晚餐 17:00–20:30；加餐任何时间可记。
- 判断顺序建议：
  1. 当前正餐未记录，且现在处于该正餐时间窗内 → 默认当前正餐。
  2. 当前/上一正餐已记录，且还没接近下一餐 → 默认加餐。
  3. 当前/上一正餐已记录，但已接近下一正餐 → 默认下一正餐。
  4. 上一餐和下一餐都已记录，或晚餐后再次记录 → 默认加餐。
- "接近下一正餐"阈值建议 45–60 分钟，原型可先用 60 分钟：早餐已记录且当前时间 ≥10:30 时可默认午餐；午餐已记录且当前时间 ≥16:30 时可默认晚餐。阈值应可配置，后续可根据用户习惯个性化。
- 默认选择要保守：系统不确定时优先选加餐，并提示用户可切换到午餐/晚餐。误把加餐记成正餐会影响复盘；从加餐手动切到正餐成本较低。
- **缺口提醒与默认推荐分离**：返回值应支持 `recommendedMeal` 与 `missedMeal` 两个字段，而不是只能返回一个默认餐次。例：`{ recommendedMeal: "加餐", missedMeal: "午餐", title: "午餐还没记录", badge: "先补午餐 · 有吃再记" }`。QuickAdd 和首页快捷入口都应能用这个结构展示"补记正餐"与"有吃再记加餐"两个行动。`recommendedMeal=加餐` 只能表示默认落点/可记录，不应在 UI 上写成"推荐加餐"。
- **餐次时间与用餐提醒合并设置**：正式入口放在 **我的 → 记录偏好 → 餐次时间与提醒**；同时在首页快捷餐次提示和 QuickAdd 餐次建议里放轻入口 **"调整餐次时间"**，让用户在系统判断不符合习惯时能就地修正。这个设置页同时管理两件事：餐次时间窗用于判断记录归属/默认餐次；用餐提醒用于本地通知推送，二者显示在同一页但语义要分清。
- **用餐提醒是本地通知**：提醒时间默认落在对应餐次时间窗内（如早餐提醒 08:00、午餐 12:30、晚餐 18:30），可单独开关。提醒时间不应反向改变餐次归类；若用户把提醒设到对应时间窗外，保存时提示调整或建议同步修改餐次时间窗。
- **作息模板切换逻辑**：常规 / 晚起 / 轮班不是独立功能页，而是一组预设的 **三餐时间窗 + 提醒时间**。用户切换模板时，同步更新下方时间窗与提醒时间；若提醒超出新时间窗，自动移动到该时间窗中点。正式开发中若用户已手动改过时间，切换模板前应轻提示"切换模板会覆盖当前餐次时间和提醒"。
  - 常规作息：早餐 05:00–10:30，提醒 08:00；午餐 11:00–14:00，提醒 12:30；晚餐 17:00–20:30，提醒 18:30。
  - 晚起晚睡：早餐/早午餐 08:30–12:00，提醒 10:00；午餐 12:30–15:30，提醒 13:30；晚餐 18:30–22:00，提醒 20:00。数据结构仍归为早餐/午餐/晚餐，UI 文案可显示"早餐/早午餐"。
  - 轮班 / 不固定：正式实现优先用"起床后 X 小时"生成三餐窗口；原型可先用 早餐 09:00–13:00、午餐 14:00–18:00、晚餐 19:00–23:30，提醒默认关闭，避免打扰。用户可手动开启本地提醒。
  - 切换并保存后影响三个地方：首页快捷餐次判断、QuickAdd 默认餐次、本地通知触发时间。设置页文案建议写成"切换作息模板会同步调整三餐时间窗和提醒时间。保存后会影响首页推荐餐次、QuickAdd 默认餐次和本地提醒。"
- **引导页只问作息类型，不做精细时间设置**：可在"记录习惯"阶段提供常规作息 / 晚起晚睡 / 轮班或不固定三类模板，用于初始化餐次时间窗；不要让新用户逐项设置早餐/午餐/晚餐时间。
- **设置必须防错**：不要允许早餐晚于午餐、午餐晚于晚餐这类无效配置。保存前校验：早餐开始 < 午餐开始 < 晚餐开始；相邻正餐至少间隔 2.5–3 小时；单个时间窗不宜超过 4–5 小时。冲突时提示"早餐时间需要早于午餐,也可以选择晚起作息模板"。更理想的交互是时间轴拖动且相邻餐次不可越界。
- 友好提示示例（由规则生成，AI 最多润色，不改变事实）：
  - 早餐已记录、午餐还早：`早餐已经记录了，离午餐还有一会儿。若现在有点饿，可以记一份轻加餐。`
  - 快到午餐：`快到午餐时间了，已为你选午餐。只是少量补充的话，也可以切到加餐。`
  - 午餐已记录、晚餐还早：`午餐已经记录了，离晚餐还有一会儿。可以记一份加餐，建议控制在 120–220 kcal。`
  - 午餐窗口已过但午餐未记：`午餐还没记录。刚才吃过的话可以补记午餐；现在只是少量补充的话，可以记加餐。`
  - 快到晚餐：`快到晚餐时间了，已为你选晚餐。只是饮品或点心的话，也可以切到加餐。`
  - 晚餐窗口已过但晚餐未记：`晚餐还没记录。刚才吃过的话可以补记晚餐；之后的饮品或点心可以记到加餐。`
  - 晚餐已记录：`晚餐已经记录了。若之后还有饮品或点心，可以记到加餐。`

### 运动补录（"+" 内次级模式）
- 定位：**轻量补录 / 估算辅助**，不是完整运动 App，不做庞大运动数据库。
- 输入三步：**类型 + 时长 + 强度**。
  - 类型 v1 只做 8 类：步行 / 跑步 / 骑行 / 游泳 / 力量训练 / 瑜伽拉伸 / 球类团课 / 其他。
  - 时长：15 / 30 / 45 / 60 分钟快捷值 + 手动输入。
  - 强度：轻松 / 中等 / 较强。
- 热量估算：基于用户体重、运动类型、时长、强度，用 MET 思路粗估；界面只显示"估算消耗约 X kcal"，并标注"基于体重、运动类型、时长和强度估算，仅供参考"。
- 去重：若同一时间段已有 HealthKit Workout 或 activeEnergy 明细，保存前提醒避免重复。
- 保存后进入今日活动来源明细，标记为"手动记录/估算"，不默认加回今日可吃额度。

### 记录方式与下游
- **拍照 / 相册 / 扫码** → 全屏相机/选择器 → **第二层确认编辑页**。
- **搜索命中标准食物 / 点常吃模板** → 可在 sheet 内直接记完。
- 搜索数据源分层（见「关键技术选型」）：个人库 → 营养库（西式商业 API + 中式数据集）→ 条码 → AI 自由文本解析 → 手动兜底。

### 第二层：确认编辑页（仅拍照/搜索/扫码需核对时升级全屏）
- 多食物条目，各带 **份量 / 热量 / 关键指标 / 来源标签 / 置信度**；**低置信度提示"建议确认份量"**；全部**可编辑**，缺失值显示"暂无可靠数据"不用 0。
- 底部：总计 + **对今日预算影响** + 保存 / 存为常吃模板 / 手动加一项。
  - "今日预算影响"在确认页/保存后提示中体现，不在首页常驻堆叠：本餐 kcal、保存后今日剩余/距目标/是否在维持区间、下一餐建议。避免写成"你需要运动消耗 X kcal"，不制造补偿性运动压力。

### 记录完成
- 保存后 **toast + 热量环动一下**，**返回原所在页面**，不强制跳转。
- 改过的条目 `status→edited`、来源可转 `user_custom`，可提示存为常吃模板。

## 健康关注层边界（硬性原则，合规护栏）【已锁定 2026-06-05】
范围：健康关注层**只做 指标追踪 + 科普提醒 + 免责声明**，不诊断、不治疗、不预测医学数值（血糖/血脂/尿酸等，除非用户手动输入或接入 CGM）。这是一道几乎零成本但挡住最大法律/合规风险的护栏（尤其先做海外，注意 SaMD 认定）。

界面体现（同一卡片骨架内，非独立页面）：
- **一次性免责弹卡**：引导勾选健康关注项后出现，说明"仅供参考、不提供医疗诊断/治疗建议、请遵医嘱"。
- **健康关注卡**：首页一张带状态色（绿/橙/红）的指标条，如"今日碳水 168/210g ●橙"，下方一句轻提示。
- **食物确认页软标签**：碳水/钠偏高时挂"碳水较高"软标签 + 一句轻提示，不报警不恐吓。
- **ⓘ 科普弹层**：指标旁小图标，点开才显示科普（含来源 + "仅供科普参考"），放二级不打扰。
- **常驻免责声明**：「我的」页底部 + 健康关注设置页固定一行小字。

合规措辞模板（句式红线）：
- ✅ 允许："建议留意…份量""可考虑…""今日钠偏高，晚餐可清淡些"。
- ❌ 禁止："糖尿病不能吃这个""会让你血糖升到 X""按这样吃能治疗/控制血压"。
- 日报建议由规则层算出、AI 只润色，**严禁预测医学数值或给治疗方案**。

## 数据模型（吸收自对比方案，骨架直接复用）
核心实体与关键约束：
- **UserProfile**：年龄/性别/身高/体重/活动水平/目标(多选)/健康关注项/目标体重/单位。
- **DailyTargets**：每日预算与关注指标，每项用 `TargetRange { min?, target?, max?, source }`。
  - `target` 用于"希望达到"(蛋白质/水/步数)，`max` 用于"别超太多"(热量/糖/钠/饱和脂肪)。
  - **来源优先级**：用户自定义且确认 > 权威库 > 品牌/条码库 > 相似食物估算 > 纯 AI 估算。用户手动设置永远优先于系统估算。
- **MealLog**：一次记录，含 `rawInput`(原始文字/语音/图片)、`items[]`、`totals`、`confidence`、`status: draft | confirmed | edited`。
- **FoodLogItem**：单个食物，含 `displayName / quantity / nutrition / source / confidence / userEdited`。
- **NutritionFacts**：热量 + 三大营养素 + 糖/纤维/钠/饱和脂肪等；**缺失字段显示"暂无可靠数据"，绝不用 0 代替**，且不参与超标判断。
- **ActivitySummary**：今日活动聚合，含 `activeEnergyKcal / steps / distance? / workouts[] / manualActivities[] / sourceStatus`。`activeEnergyKcal` 优先来自 HealthKit `activeEnergyBurned`；Workout 和步数主要用于解释来源。
- **ManualActivityLog**：手动运动补录，含 `type / durationMinutes / intensity / estimatedKcal / source: manual_estimate / timeRange?`。估算值必须标注为估算；若时间段与 HealthKit Workout 重叠，保存前提示去重。

## 日报生成：规则层 + AI 文案层（双层）
- **规则层**先用明确数据算出 `fact(事实) / cause(原因) / action(动作)`，例如"脂肪超目标 28% / 晚餐炸鸡奶茶贡献最大 / 明天晚餐换蒸煮蛋白"。
- **AI 层**只把结构化结果翻译成自然、友好的话术，**不承担医学判断**。
- 健康关注项措辞受限：只能"建议留意碳水/钠"，不能"你应该如何治疗"。

### 首页下一步建议：规则模板优先
- 首页提醒先用 **规则层 + 参数化模板**，不让 AI 自由生成行为建议。AI 可选只做润色，不能改事实、不能给医疗化建议、不能建议补偿性运动。
- 规则层输入：`goalProfile / nextMeal / consumed / target or range / remaining / proteinRemaining / macroStatus / activityLevel / workoutToday / loggedMeals`。
- 模板示例：
  - 减重正常："晚餐建议 300–450 kcal，蛋白质还差 42g。可选鱼、鸡蛋、豆腐或鸡胸肉。"
  - 减重接近上限："今天余量不多，下一餐以蛋白质和蔬菜为主。"
  - 减重已超："今天已经略超，不用补偿运动，明天回到节奏就好。"
  - 维持："今天在维持区间内，下一餐正常吃，留意蔬菜和蛋白质。"
  - 增肌："晚餐建议 650–850 kcal，蛋白质还差 48g。训练日可加一份主食。"
- 食物建议只给**食物类型/选项**，不生成具体食谱或餐单，守住"不做 Recipes / Meal Plan"边界。

## 置信度与来源标注（建立信任的关键）
- 每条食物卡显示**数据来源标签 + 置信度**(高/中/低)。
- 低置信度触发"建议确认份量"：图片含混合菜/汤/酱料/遮挡、无法判断份量、数据库无明确匹配、关键指标缺失时。
- 确认/修改后：`status→edited`、`userEdited→true`、来源可转 `user_custom`，并提示"保存为常吃模板"。

## HealthKit 细节与边界
- **第一版只读不写**：步数、活动能量、训练、体重；营养数据先存 App 内，待流程稳定后再写入(且只写用户确认过的记录)。
- `activeEnergyBurned` **不含基础代谢**；**不要把静息代谢加进"可吃额度"**(否则用户误以为躺着也能多吃)。
- **不鼓励补偿性进食**：消耗高时不说"你可以多吃 400 kcal"，改说"如饿可优先补蛋白质和高纤维"。
- 权限**分场景请求**：说明价值后再弹系统授权，不开屏全要；心率/睡眠/营养写入暂不请求。
- 体重用 7 日平均/趋势，单日上升不做负反馈。

### HealthKit 数据整合策略
- v1 默认读取：
  - 必读：`stepCount`、`activeEnergyBurned`、`bodyMass`。
  - 强烈建议读：`HKWorkout`、`distanceWalkingRunning`。
  - 后置：`sleepAnalysis`、`heartRate`、`restingHeartRate`、`bodyFatPercentage`、`waistCircumference`。
- 活动消耗聚合优先级：
  1. 有 `activeEnergyBurned`：用它作为今日活动消耗总数。
  2. 没有 `activeEnergyBurned`，但有 `HKWorkout.totalEnergyBurned`：用 Workout 消耗 + 必要时步数估算补充，并标注估算。
  3. 只有步数：基于步数 + 用户体重粗估，显示"约 X kcal / 基于步数估算"。
  4. 没有权限或无数据：显示未同步状态 + 连接健康 App / 手动记录入口。
- **避免重复计算**：Apple Watch/iPhone 的步数、训练和日常活动可能已汇总进 `activeEnergyBurned`；若读取到 activeEnergy，不再把步数估算或 Workout 热量额外相加。Workout 和步数用于解释来源，如"步行 210 · 训练 110"。
- 首页展示：
  - 步数卡：`6,840 / 8,000`，可隐藏或变成未同步状态。
  - 今日活动卡：`320 kcal · 步行 210 · 训练 110`，点击进活动详情。
  - 不默认展示心率、睡眠、喝水；喝水可作为可开关卡片，睡眠用于洞察提示，心率放健康数据页/运动详情，避免医疗化。
- 活动详情二级页展示：
  - 总活动消耗与来源。
  - 来源明细：步行与日常活动 / Workout / 手动记录。
  - 未同步空状态："健康数据未同步；步数和活动消耗会暂时隐藏，首页仍保留饮食记录、今日目标和蛋白质建议。"
  - 手动补录轻入口，如"没有同步到运动？补录一项 ›"；点击后进入 QuickAdd 运动模式或运动补录 sheet，再展示类型 + 时长 + 强度 + 估算消耗。活动详情页本身不常驻大表单。
- 无权限时不阻断：饮食记录、今日目标、体重手输、运动手动补录照常可用；不要反复弹权限，也不要让用户觉得不授权就无法使用。

### Upsell / 付费对比呈现规范
原则：**对比卖的是"深度/省力"，不是"精度"**；只对比能稳定兑现的能力（数据库深度、规则洞察、省时），不对比"AI 精度"。
- 适合做左右对比/锁定预览的位置：
  - **食物详情"深度分析"**：免费=名称+热量+基础营养素；VIP=完整营养拆解 + 健康关注指标 + 来源/置信度 + 改进建议（靠 DB+规则，可靠）。
  - **趋势/周报"AI 洞察"**：免费=数字图表；VIP=洞察 + 改进建议（规则层算事实、AI 润色）。
  - **"拍照即记 vs 手动输入"省力对比**：适合做付费墙主视觉，卖省力、不涉精度承诺，最安全。
- 不适合/高风险：暗示"AI 给精确权威数字"的对比（自打脸 + 健康宣称风险）；把核心记录/每日 Dashboard 锁进付费墙（杀留存）；故意把免费版做丑做残（dark pattern，伤口碑/审核风险）。
- 做法：**上下文触发**（点到锁定的深度分析/洞察、或用完免费 AI 次数时才出）；**用用户真实数据做模糊+加锁预览**，胜过通用 mockup；时机要"挣来"（用几天后再推）；保持克制美学，显式左右对比页留给专门付费墙，不每条结果弹窗。
- 注意：右侧 VIP 内容指 **AI 分析结果**，不是 AI 生成食物图片（后者已永久砍）。
